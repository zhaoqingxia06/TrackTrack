# 操作盘点与埋点设计

## 盘点方法

- 从路由、页面入口、组件、交互处理函数、API 调用及运行页面互相核对；记录页面、状态、角色、入口路径、操作点、交互方式、条件和源码位置。覆盖表单、链接、按钮、Tab、开关、选择、展开、弹层、滚动/拖拽、键盘与触屏、结果及错误状态；按产品实际情况取舍。
- 对每个操作点标注已设计/已有事件/不采集及理由/无法访问或待确认。动态列表用稳定组件 ID 与安全的业务分类，不把每条内容变成事件类型；记录可验证的覆盖率与范围，不把静态扫描当运行覆盖。
- 先确定分析问题，再决定事件和属性；全量盘点不意味着采集所有输入、鼠标移动或页面内容。

## 事件方案每行至少包含

页面/状态、操作点与稳定标识、事件名称及版本、事件类型（用户操作/业务结果/系统）、触发时机与前置条件、一次触发计数规则、公共字段、专有字段及类型/必填/枚举、上报字段、用途、去重身份、负责人或来源、隐私处理、验收方式、实现/验证状态。将不存在的字段标待定，不虚构。

公共字段建议：event_id（每次唯一）、event_name、schema_version、occurred_at（含时区或 UTC）、匿名身份、session/trajectory_id、页面路由标识、组件标识、应用版本、环境、顺序号；服务端另记接收时间。具体按项目需要裁剪。避免直接采集 URL 参数、输入值、文本、账号、令牌、敏感信息；使用字段白名单。

- 点击与成功分离：点击提交只能证明意图；只有真实成功回调或服务端结果才能记录成功，失败另记结果。开关按打开/关闭状态转换；不要为普通一次性操作编造关闭事件。
- 持续过程有 process_id，开始、有效结束、结束原因与完整性；缺结束保留未确认和最后观测时间，不推定精确时长。触发时机要写明发生在调用前、状态实际变化后或响应结果后，避免重复上报。
- 明确跨页面、刷新、多标签、后台、超时和退出是否形成新轨迹；无法可靠观察退出时不伪造结束。身份去重单位如匿名浏览器、登录账户要如实命名，不等同自然人。
- 方案中以具体一行示例解释事件与参数：例如 `tab_selected` 在目标 Tab 实际切换成功后上报 `from_tab`、`to_tab`，不发送标签中的用户内容；具体名称和字段应适配产品。

## 从指标反推采集

- 为每个重点事件写具体问题、可计算指标及来源，不只写“统计 PV/UV”；输出事件清单与公共参数字典，按需关联页面截图或组件定位，便于产品和开发共同核对。原型只反映设计意图，还需结合运行页面和源码核实。
- 逐类检查页面曝光、导航/Tab、按钮与开关、列表与弹窗、输入与搜索、媒体、设置、收藏和异步任务；按实际产品决定是否采集，不机械生成所有事件。曝光需要定义可见条件、去重和重复曝光规则，页面加载不自动等同用户看到。
- 先列产品要回答的问题及可用指标，倒推事件、关联 ID 和字段；再与全量操作盘点互相校验。记录已有事件能否支持指标以及采集缺口。若要求 Excel，按目标项目和需求选择格式与工具，不把某个脚本和固定公共参数当通用协议。
